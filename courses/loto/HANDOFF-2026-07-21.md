## How the work runs (conventions that matter)

- **Use the authenticated GitHub MCP** — `get_file_contents`, `create_or_update_file` (pass `sha` to update an existing file), `get_pull_request_files` for diffs. NOT the unauthenticated API (rate-limits, and hammering it crashes conversations). `raw.githubusercontent.com` via fetch works and handles slashed branch names.
- **The Sonnet loop:** Claude writes a brief → Sean's Sonnet (in Claude Code) implements on a branch (off `main`, never stacked — §M5) → hands back a branch + change note + screenshots → **Claude independently verifies by diffing the actual files, never trusting the handback** → Sean signs off → merge. Claude cannot see Sonnet's `claude.ai/code` artifacts (client-rendered; a fetch returns only the shell) — rely on the repo (the branch + change-note markdown are readable).
- **Content vs. presentation:** presentation passes freeze content (verify content-*preservation* — a word-multiset diff, allowing an image path to drop when a stark-cut goes clean-ground). Content passes change content (verify *only* the approved changes; no sourced claim's meaning altered). The frozen SOURCE (`courses/loto/sources/`) is the authority; the course renders it, never overrides it.
- **The content-pass interaction is the app's core loop:** the AI proposes *source-validated* fixes and flags each for the domain-expert human to decide (Sean did exactly this on #79's four items). The AI guarantees source *fidelity*; the human owns domain *appropriateness*. Escalating Sonnet→Opus shrinks the AI-error half of review, not the human-decision half — that stays with the human at any model size.
